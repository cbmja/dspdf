# MySQL에서 MSSQL로 DB 마이그레이션 작업 기획서

| 항목 | 내용 |
|---|---|
| 대상 시스템 | dspdf 우편 제작 요청 및 진행 상태 관리 시스템 |
| 전환 방향 | MySQL에서 Microsoft SQL Server로 전환 |
| 작성일 | 2026년 11월 8일 |
| 문서 버전 | 1.0 |
| 검토 대상 | 개발 담당자, DBA, 인프라 담당자, 서비스 운영 담당자, 연계 시스템 담당자 |
| 작업 방식 | 서비스 쓰기를 중지한 뒤 전체 데이터를 이관하는 방식 제안 |
| 일정과 중단 시간 | 아래 일정은 계획 예시이며 리허설 측정 후 확정 |

이 작업은 인프라의 DB 표준 변경에 맞춰 현재 MySQL 기반 시스템을 MSSQL로 이전하는 것을 목적으로 한다. 기존 API와 화면, 작업 상태 처리, 데이터 보관 방식을 유지하면서 DB 스키마와 데이터를 이관하고 JDBC 연결 및 MyBatis SQL을 변경한다. 운영 전환은 데이터와 파일의 일관성을 확보한 상태에서 수행하며, 신규 쓰기 허용 전후를 구분해 복구 절차를 준비한다.

드라이버 교체만으로는 전환할 수 없다. 현재 코드에서 확정된 SQL 문법 변경은 현재 시간 함수 5곳과 페이징 2곳이다. 실제 스키마, 검색 컬럼 자료형, 문자 정렬, 트랜잭션 및 운영 구성에 따라 추가 변경이 필요할 수 있다.

## 1 추진 배경과 목표

### 1.1 추진 배경

인프라 운영 DB를 MSSQL로 변경해야 하므로 애플리케이션의 MySQL 의존성을 제거한다. 이기종 DB 간에는 시간 함수, 페이징, 문자열 및 날짜 자료형, 자동 증가 키, 정렬과 비교 방식에 차이가 있어 스키마와 데이터, 애플리케이션을 함께 전환한다.

### 1.2 목표

1. 기존 4개 업무 테이블의 승인된 이관 대상 데이터를 누락 없이 이전한다.
2. 개별 및 대량 우편 요청 접수, 조회, 오류 기록, 상태 변경이 기존과 동일하게 동작하도록 한다.
3. PDF와 JSON 파일의 위치 및 처리 상태를 DB 데이터와 일치시킨다.
4. 운영 전환 중 발생한 요청의 처리 여부를 식별하고 중복 처리와 유실을 방지한다.
5. 실패 시 신규 데이터까지 보존하면서 기존 환경으로 복구할 수 있는 절차를 확보한다.

### 1.3 완료 판단 기준

| 구분 | 완료 기준 |
|---|---|
| 데이터 | 중지 시점 원본과 대상의 테이블별 건수, 키 집합, 정규화된 전체 행 비교 결과 일치 |
| 업무 기능 | 필수 테스트 전 항목 통과, 미해결 중대 결함 없음 |
| 파일 | DB에 연결된 PDF의 존재와 위치, 작업별 JSON 및 파일 처리 상태 일치 |
| 성능 | 합의한 운영 부하에서 응답 시간, 처리량, 오류율 기준 충족 |
| 운영 | 백업과 복구, 모니터링, 계정 권한, 스케줄러 단일 실행 검증 완료 |
| 전환 | 리허설에서 측정한 이관 및 복구 시간이 승인된 점검 시간 안에 수용 가능 |
| 인수 | DBA, 개발, 운영, 업무 담당자의 검증 결과 및 서비스 재개 승인 기록 확보 |

### 2.2 대상 테이블

| 테이블 | 주요 데이터 | 저장 특성 | 기존 보관 동작 |
|---|---|---|---|
| MASTER | MASTER_KEY, TOTAL_SEND_CNT, SEND_CNT, STATUS, RECEIVED_TIME, STATUS_TIME, TYPE | 작업 묶음 생성 후 건수와 상태 갱신 | 삭제 대상 상태에서 상태 시각이 1개월보다 오래되면 삭제 |
| DETAIL | PK, TR_KEY, MASTER, 수신자와 주소, 고객번호, 배송과 인쇄 정보, PDF_PATH, PDF_NM, SAVE_DATE | 요청별 추가, 파일 이동 시 경로 갱신 | 관련 MASTER 삭제 시 먼저 삭제 |
| ERROR | ID, ERROR_MESSAGE, CREATE_DATE, MASTER_KEY, ERROR_CODE | 요청 오류와 DB 및 파일 처리 오류 발생 시 추가 | 애플리케이션에 정기 삭제 로직 없음 |
| STATUS | NUM, STATUS_CODE, STATUS_NAME, WAIT_TIME, CHANGE_TYPE, CREATE_DATE | 상태 코드와 전환 규칙 조회 | 업무 요청에 따라 누적되지 않는 기준 정보 |

MASTER_KEY는 대량 작업에서는 TR_KEY, 단일 작업에서는 날짜 기준 묶음에 사용된다. DETAIL.MASTER와 MASTER.MASTER_KEY는 코드상 연결 관계이며, 물리적 외래 키 유무는 실제 DDL에서 확인한다. ERROR.MASTER_KEY는 오류 추적용 값으로 사용되므로 MASTER 삭제 후에도 오류가 남을 수 있다.

DETAIL에는 개인정보가 포함되고 ERROR_MESSAGE에는 요청 파라미터나 상세 오류가 들어갈 수 있다. 검증 결과와 이관 파일에도 동일한 접근 통제를 적용한다.

### 2.3 스케줄과 파일 연계

| 주기 | 코드상 작업 | 전환 시 영향 |
|---|---|---|
| 매일 14시 3분 | 당일 단일 요청 묶음 수신 완료 처리, JSON 생성, receiving에서 complete로 파일 이동 | DB와 파일을 동시에 변경하므로 중지와 재개 시점 통제 필요 |
| 3분 간격 | AUTO 상태의 대기 시간 경과 확인, 다음 상태 전환, 디렉터리 확인 | 비교 대상 시간대와 스케줄러 중복 실행 검증 필요 |
| 매일 19시 | 삭제 대상 MASTER와 관련 DETAIL 정리 | 검증 전에 실행되면 이관 직후 건수가 달라질 수 있음 |

삭제 대상은 STATUS_CODE 오름차순 목록의 끝에서 두 번째 상태이다. 코드 주석의 ‘마지막 상태’와 실제 선택 방식이 다르므로, 운영 STATUS 데이터로 실제 대상 코드를 확정한다. 삭제 기준은 최초 저장 시간이 아니라 MASTER.STATUS_TIME이며, 고정 30일이 아니라 달력 기준 1개월이다. 이 정기 작업에는 PDF 파일 삭제가 포함되어 있지 않다.

## 4 목표 설계와 애플리케이션 변경

### 4.1 기본 설계 원칙

애플리케이션은 기존 MyBatis 구조와 업무 키를 유지한다. 이관 시 기존 키와 시각을 보존하며 업무 상태를 일괄 초기화하지 않는다. 인프라 변경이 DB에 한정되면 PDF 저장 경로와 파일 서버는 유지한다. 스키마명은 운영 표준에 따라 확정하고, 애플리케이션 기본 스키마 또는 명시적 테이블 참조 방식으로 일치시킨다.

### 4.2 JDBC와 연결 설정

| 파일 | 계획된 변경 | 검증 |
|---|---|---|
| pom.xml | MySQL JDBC 제거, Microsoft의 mssql-jdbc 추가 | Java 17 및 Spring Boot 조합으로 빌드와 실행 |
| application.yml 또는 배포 환경 설정 | MSSQL URL, SQLServerDriver, 계정과 인증서 설정 반영 | 실제 배포 호스트에서 연결과 CRUD 권한 확인 |
| 배포 설정 | 운영 비밀번호 외부 주입, 이전 설정 보관 | 로그와 산출물의 비밀번호 노출 방지 |

드라이버 버전은 Java 17과 대상 SQL Server를 지원하는 사내 승인 버전으로 고정한다. 운영 계정은 필요한 SELECT, INSERT, UPDATE, DELETE 권한으로 제한하고, 스키마 생성 및 대량 적재 계정은 분리한다. JDBC URL은 Microsoft 공식 형식을 따른다.[4]

```yaml
spring:
  datasource:
    url: jdbc:sqlserver://${DB_HOST}:${DB_PORT};databaseName=${DB_NAME};encrypt=true;trustServerCertificate=false
    driver-class-name: com.microsoft.sqlserver.jdbc.SQLServerDriver
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
```

위 예시는 SQL 인증 기준이다. 통합 인증을 사용하면 별도 설정을 확정한다. 운영에서는 서버 이름과 인증서 이름, 신뢰 체인을 맞춘다. 인증서 오류를 해결하기 위한 목적으로 인증서 검증 해제를 운영 기본값으로 채택하지 않는다. MySQL의 serverTimezone과 characterEncoding URL 파라미터는 그대로 복사하지 않는다.

### 4.3 확정된 SQL 변경 7곳

| 파일 | 구문 | 개수 | 변경안 |
|---|---|---|---|
| mapper/Master.xml | save, updateStatus, updateStatusAndTotalCnt의 NOW() | 3 | CURRENT_TIMESTAMP |
| mapper/Detail.xml | save의 NOW() | 1 | CURRENT_TIMESTAMP |
| mapper/Errors.xml | save의 NOW() | 1 | CURRENT_TIMESTAMP |
| mapper/Master.xml | selectMastersByPage의 LIMIT | 1 | OFFSET 및 FETCH |
| mapper/Errors.xml | selectErrorsByPage의 LIMIT | 1 | OFFSET 및 FETCH |

현재 시간 함수는 기존 초 단위 업무 의미를 유지하는 방향으로 CURRENT_TIMESTAMP를 사용한다. 목표 날짜 정밀도에 따라 SYSDATETIME 사용 여부를 DBA와 확정한다. DB에서 생성한 시각과 Java LocalDateTime이 동일한 업무 시각을 의미하는지 검증한다.[3]

```sql
-- MySQL 페이징
ORDER BY ${sortCate} ${sort}
LIMIT #{startNum}, #{pageElement}

-- MSSQL 페이징
ORDER BY ${sortCate} ${sort}
OFFSET #{startNum} ROWS
FETCH NEXT #{pageElement} ROWS ONLY
```

OFFSET 및 FETCH는 SQL Server 2012 이상에서 지원한다. 실제 대상 버전과 호환성 수준을 확인한다. startNum은 현재도 0부터 시작하는 오프셋이므로 계산 의미를 유지할 수 있다. pageElement는 양수여야 하며 0, 음수, 과도한 값에 대한 입력 처리를 검증한다. 같은 상태 시각이나 생성 시각을 가진 행은 순서가 모호해질 수 있어, 허용된 정렬 조건 뒤에 유일 키를 보조 정렬로 추가하는 최소 보완을 검토한다.[2]

### 4.4 추가 호환성 검토

| 항목 | 점검 내용 | 대응 원칙 |
|---|---|---|
| LIKE 검색 | 숫자나 날짜 컬럼에 문자열 검색을 적용하는 경로 | 허용 검색 컬럼별 실행 검증 후 필요한 위치만 명시적 변환 |
| CONCAT | 일반 문자열 결합은 지원하지만 NULL을 빈 문자열로 취급 | NULL 검색값의 기존 처리 및 기대 결과 확인 |
| 동적 SQL | cate, sortCate, sort가 문자열 치환으로 삽입됨 | 허용 컬럼과 ASC 및 DESC를 서버에서 검증하며 요청값 직접 삽입 금지 |
| 문자 비교 | 대소문자, 악센트, 공백, 한글 정렬 및 키 충돌 | 원본과 대상 collation 비교 및 충돌 사전 검사 |
| DTO 매핑 | 대문자 컬럼, LocalDateTime, NULL과 숫자 매핑 | 실제 JDBC 및 MyBatis 조회로 검증 |
| 트랜잭션 | 신규 DETAIL 저장 후 MASTER 생성 및 갱신, 다건 삭제 | 중간 실패와 동시 요청에서 부분 반영 여부 검증 |
| 오류 처리 | DB 오류 후 ERROR 저장도 같은 DB를 사용 | DB 장애 시 ERROR 미기록을 고려해 애플리케이션 로그 함께 확인 |
| 동시성 | 동일 작업의 SEND_CNT를 읽고 증가시켜 저장 | 동시 접수 시험에서 건수 불일치 시 공유 저장 로직 최소 수정 |

7곳은 명시적인 문법 교체 수량이며 전체 작업량을 의미하지 않는다. 추가 수정이 생기면 사유와 영향을 변경 목록에 반영한다. STATUS 조회 SQL은 현재 기준 문법 교체 대상이 없지만 대상 스키마와 데이터 매핑 검증에는 포함한다.

## 5 스키마와 데이터 이관 설계

### 5.1 원본 조사 산출물

DBA는 원본 테이블별 SHOW CREATE TABLE 결과와 인덱스, PK 및 FK, UNIQUE, NULL 허용, 기본값, 문자셋, collation, 자동 증가 현재값을 수집한다. 트리거, 뷰, 프로시저, 이벤트, 외부 배치와 계정별 의존성도 조사한다. 애플리케이션 SQL에 나타나지 않는 객체는 처리 방식을 별도로 결정한다.

각 테이블의 전체 건수, 데이터 및 인덱스 크기, 일별 증가량, 최소 및 최대 시각, 컬럼별 최대 문자열 길이, NULL과 빈 문자열 분포, 키 중복과 고아 데이터 현황을 기록한다. ERROR는 자동 삭제가 없어 누적 규모가 클 수 있으므로 실제 이관 시간을 별도 측정한다.

### 5.2 자료형 매핑 원칙

| 원본 특성 | MSSQL 설계 방향 | 반드시 확인할 사항 |
|---|---|---|
| 일반 정수 | INT 또는 BIGINT 등 범위에 맞는 형 | UNSIGNED 사용 여부와 최대값 |
| 자동 증가 정수 | 필요한 컬럼에 IDENTITY | 기존 ID 유지와 다음 생성값 충돌 방지 |
| 이름과 주소, 메시지 | NVARCHAR를 기본 후보로 검토 | 실제 길이와 보조 문자, 인덱스 키 제약, JDBC 파라미터 타입 |
| 긴 오류 메시지 | 길이에 따라 NVARCHAR(MAX) 등 결정 | 잘림 여부, 적재 도구와 검증 도구의 길이 한계 |
| MySQL DATETIME 또는 TIMESTAMP | 업무 의미에 맞는 DATETIME2 및 정밀도 | 시간대 변환 여부, 소수초, 비정상 날짜 |
| 플래그 및 코드 문자열 | 의미와 길이를 유지한 문자형 | NULL, 빈 값, 앞자리 0 보존 |

실제 DDL 확보 전에는 컬럼 길이와 물리 키를 확정하지 않는다. 고객번호, 우편번호와 업무 키는 숫자처럼 보여도 기존 문자열 의미와 앞자리 0을 유지한다. SQL Server의 TIMESTAMP는 날짜가 아닌 ROWVERSION 계열이므로 MySQL TIMESTAMP를 같은 이름으로 매핑하지 않는다.[5]

시간 데이터는 원본 저장값, MySQL 세션 시간대, 현재 JDBC 설정, JVM 시간대의 관계를 먼저 확인한다. 기존 URL의 serverTimezone=UTC만으로 기존 데이터가 모두 UTC라고 판단하지 않는다. 전환 중 기존 STATUS_TIME을 현재 시각으로 갱신하면 자동 상태 변경과 삭제 기준이 바뀌므로 원래 값을 보존한다.

### 5.3 키와 참조 관계

기존 PK와 UNIQUE를 원본 의미대로 이관한다. ERROR.ID가 원본에서 자동 증가로 정의되어 있다면 IDENTITY로 생성하고 기존 ID를 보존하는 적재 방식을 사용한다. 적재 후 identity 현재값과 다음 삽입 결과를 검증한다. STATUS.NUM의 자동 증가 여부도 DDL로 확인한다.

컬럼 연결 관계만 보고 새로운 FK를 임의로 추가하지 않는다. 접수 코드는 DETAIL 저장 후 MASTER를 생성할 수 있고, ERROR는 작업 삭제 후 남을 수 있어 새로운 FK가 기존 처리 순서를 막을 수 있다. 기존 FK가 있다면 적재 순서와 제약조건 재검증 절차를 설계하고, 존재하지 않는 FK의 도입은 별도 설계 변경으로 판단한다.

### 5.4 이관 도구와 적재 절차

SSMA for MySQL을 우선 후보로 평가한다. SSMA는 객체 평가, 형 변환, 스키마 변환 및 데이터 이관을 지원하지만 애플리케이션 MyBatis SQL 변경까지 대신하지 않는다. 대상 버전과 실행 환경 지원 여부를 확인한 뒤 선정한다.[1]

1. 개발용 MSSQL에 변환된 스키마를 생성한다.
2. 테이블별 자료형 매핑과 변환 경고를 검토하고 수정한다.
3. STATUS, MASTER, DETAIL, ERROR 순서로 전체 데이터를 적재하는 방안을 검증한다. 실제 FK 의존성이 다르면 순서를 조정한다.
4. 기존 키와 시각을 보존하고, 문자와 줄바꿈, NULL, 빈 값, 긴 오류 메시지가 손실되지 않도록 적재한다.
5. 제약조건과 인덱스를 확인하고 통계를 정비한 뒤 전체 데이터 검증을 수행한다.
6. 동일 작업을 운영 규모 복제 데이터로 반복해 실행 시간과 재시작 방법을 확정한다.

도구 사용이 불가능하면 전용 추출 및 적재 스크립트를 별도 산출물로 준비한다. CSV를 사용할 경우 구분자, 따옴표, 줄바꿈, BOM, 인코딩, NULL 표기, 날짜 형식을 명시한다. 운영에서 처음 수동으로 가공하는 절차는 허용하지 않는다. 재실행은 데이터가 중복되지 않도록 승인된 대상 스키마 재초기화 또는 검증된 재개 방식으로 수행한다.

## 6 이관 방식과 데이터 검증

### 6.1 기본 전환 방식

4개 테이블에 대한 전체 이관과 단일 쓰기 DB 전환을 기본안으로 한다. 테이블 수가 적다는 이유로 점검 시간이 짧다고 가정하지 않으며 데이터량, 파일 처리, 검증, 복구 시간을 리허설에서 측정한다.

운영 쓰기를 중지한 동일 기준 시점의 DB와 파일 상태를 확보한다. MySQL에서 MSSQL로 계속 쓰기를 흘리면서 단순히 테이블을 순서대로 복사하면 서로 다른 시점의 작업이 섞일 수 있으므로 최종 이관에는 사용하지 않는다. 초기 적재와 증분 동기화는 중단 시간 요구가 전체 이관으로 충족되지 않을 때 별도 계획으로 설계한다.

### 6.2 데이터 정합성 검증 기준

| 검증 항목 | 방법 | 합격 기준 |
|---|---|---|
| 전체 건수 | 최종 동결 원본과 MSSQL의 테이블별 COUNT 비교 | 승인된 제외 데이터 외 차이 0 |
| 키 집합 | 테이블별 원본 및 대상 키 전체 비교 | 누락 및 추가 키 0 |
| 전체 값 | 키 기준 전체 행을 정규화해 비교 | 승인된 타입 표현 차이 외 차이 0 |
| 그룹 통계 | MASTER별 DETAIL 수, 상태별 MASTER 수, 일자별 ERROR 수 비교 | 원본 대비 차이 0 |
| 기준 정보 | STATUS 코드, 이름, 순서, 전환 방식, 대기 시간 전량 비교 | 차이 0 |
| 참조 상태 | DETAIL의 MASTER 누락과 미정의 상태 코드 비교 | 원본 대비 신규 불일치 0 |
| 자동 증가 | 기존 ID와 새 ID 생성 시험 | 충돌 없음, 다음 값 정상 |
| 개인정보와 문자 | 한글과 특수문자, 최대 길이, 주소와 메시지 비교 | 깨짐과 잘림 없음 |
| 시간 | 대표 행 및 전체 날짜값 비교, 상태 경계값 시험 | 의도하지 않은 시각 이동 없음 |
| 파일 | 연결된 파일의 경로, 크기, 필요 시 해시 및 처리 단계 대조 | 신규 누락과 잘못된 연결 없음 |

원본에 이미 존재하는 고아 행이나 건수 불일치는 이관 중 임의로 삭제하거나 수정하지 않는다. 원본 결함 목록과 업무 승인 결과를 남기고, 신규 불일치와 구분한다. TYPE별 TOTAL_SEND_CNT와 실제 DETAIL 수는 수신 중 상태에서 다를 수 있으므로 모든 상태에 일률적인 일치 조건을 적용하지 않는다.

전체 행 비교는 NULL과 빈 문자열을 구분하고 날짜 정밀도, 숫자 표현, 문자열 인코딩을 통일한 외부 비교 도구로 수행한다. DB별 CHECKSUM 함수를 서로 비교해 정합성을 판정하지 않는다. 해시 비교를 사용할 경우 키별 정렬, 컬럼 순서, 길이 구분, NULL 표현을 고정하고 불일치 행을 원문으로 재검증한다. 표본 확인은 전체 비교를 보완하는 수단으로 사용한다.

### 6.3 성능 검증과 잠정 기준

개발과 운영 담당자는 원본 환경에서 동일 데이터와 부하로 접수 응답 시간, 목록 및 오류 검색 응답 시간, 처리량, 오류율을 측정한다. MSSQL에서도 같은 조건으로 재현하고 DB CPU, 메모리, 디스크 지연, 잠금 대기, 교착, 연결 풀 사용률을 비교한다.

정량 기준의 초안은 핵심 API와 목록 조회의 p95 응답 시간이 원본 대비 20퍼센트 이상 악화되지 않고 기존 업무 타임아웃을 넘지 않는 것으로 한다. 실제 수치와 부하 조건은 기준선 측정 후 운영 담당자가 확정한다. 측정값 없이 ‘성능 정상’으로 통과 처리하지 않는다.

검색은 중간 문자열 LIKE와 깊은 페이지를 포함한다. 성능 문제가 있으면 실제 실행 계획을 기준으로 기존 인덱스를 조정하고, 검색 기능 변경이나 전면적인 페이징 개편은 별도 범위로 판단한다.

## 8 스케줄러 통제와 파일 일관성

### 8.1 스케줄러 중지 방식

현재 코드에는 EnableScheduling과 직접 선언된 Scheduled 메서드가 있다. 일반 설정값 하나로 전부 중지된다고 가정하지 않는다. 최종 이관 시에는 모든 애플리케이션 인스턴스를 중지하고, 외부 배치와 직접 DB 변경 경로도 차단한다.

MSSQL 기동 검증은 요청과 파일 소비자를 통제한 상태에서 진행해야 한다. 이를 위해 스케줄러 구성의 조건부 활성화 등 검증된 최소 제어 수단을 준비하고, 비활성 상태에서 3분 작업과 정시 작업이 실행되지 않는지 확인한다. 여러 인스턴스가 있는 경우 한 인스턴스만 스케줄을 실행하도록 운영 구성을 확정한다.

### 8.2 파일 상태 보존

DB 이관만 수행하더라도 receiving과 complete 디렉터리를 변경하는 프로그램과 외부 파일 소비자를 함께 파악한다. 최종 DB 동결 시 파일 목록, 경로, 크기, 수정 시각과 진행 중 작업 목록을 기록한다. 파일 이동이 끝나지 않은 작업은 처리 완료 여부를 확인한 뒤 동결 기준에 포함한다.

앱 서버 또는 저장소도 이전한다면 파일 복사 시간과 증분 복사, 경로 호환성, 권한, 백업을 별도 작업으로 추가한다. 현재 경로 처리에는 Windows 경로 구분자를 사용하는 코드가 있으므로 운영체제 전환은 DB 변경과 별도 영향 분석이 필요하다.

외부 출력 또는 발송이 시작된 작업은 DB를 복구해도 업무 처리가 되돌아가지 않는다. 전환 전후 처리 목록을 확보하고 재전송 전에 발송 및 파일 소비 이력을 대조한다.

### 9.2 일정 초안

환경과 권한이 준비된 뒤 약 10영업일의 실행 일정을 가정한다. 이는 확정 공수나 완료일이 아니며 인프라 조달, 보안 승인, 데이터 규모, 신규 결함 해결 기간은 별도 반영한다.

| 기간 예시 | 계획 |
|---|---|
| 1일차와 2일차 | 현황 조사, 대상 설계, 전환과 복구 기준 합의 |
| 3일차와 4일차 | 스키마 생성, 코드 변경, 개발 데이터 이관 |
| 5일차와 6일차 | 전체 비교, 기능 및 부하 시험, 결함 수정 |
| 7일차 | 전체 전환과 롤백 리허설 |
| 8일차 | 보완, 재검증, 운영 전환 승인 |
| 9일차 | 승인된 점검 시간에 운영 전환 |
| 10일차 | 초기 안정화와 운영 인수, 미완료 관찰 항목 이관 |

관찰 기간은 최소 다음 업무 주기의 피크 접수, 14시 3분 마감, 19시 삭제, 백업 성공을 포함하도록 설정한다. 휴일이나 전환 시각에 따라 10일차 이후까지 관찰이 이어질 수 있다.

### 9.3 중단 시간 산정

중단 시간은 요청 차단 및 처리 종료 시간, 최종 백업, 데이터 추출 및 적재, 인덱스와 통계 정비, 전체 비교, 앱 기동 및 업무 시험, 재개 승인 시간을 합산해 산정한다. 각 단계의 측정값과 복구 소요 시간을 기록하고 여유 시간을 추가한다.

최종 롤백 판단 시각은 ‘점검 종료 시각에서 검증된 복구 시간과 여유 시간을 뺀 시각’으로 정한다. 그 시각까지 필수 검증이 끝나지 않으면 재개를 강행하지 않는다. 14시 요청 묶음 기준, 14시 3분 마감, 19시 삭제를 가급적 피하고, 정시 작업을 건너뛸 경우 누락분의 수동 처리 절차를 승인받는다.

T0는 기존 DB와 파일 변경이 정지한 기준 시각이며 T1은 대상 환경에서 첫 쓰기를 허용한 시각이다. 기동 시험용 요청도 쓰기에 해당하므로 T1을 일반 사용자 재개 시각으로만 정의하지 않는다. 시험 데이터는 통제된 키로 구분하고 기존 파일이나 실제 우편 발송에 영향을 주지 않게 한다.

HTTP 차단만으로 이미 처리 중인 요청이 중단되는 것은 아니다. DB 세션과 앱 로그에서 완료 여부를 확인한다. 성공 응답을 받지 못한 요청은 TR_KEY와 RECV_NUM, 업무 이력으로 처리 여부를 대조하고 송신 측 재시도 목록과 일치시킨다.

## 11 진행과 중단 판단 기준

### 11.1 서비스 재개 조건

- 원본과 대상의 필수 정합성 검증을 통과했다.
- 정상 및 오류 접수, 조회, 상태 변경, 파일 처리 시험을 통과했다.
- STATUS 기준 데이터와 삭제 대상 코드를 확인했다.
- 시간대와 1개월 삭제 경계 동작을 확인했다.
- 스케줄러를 단일 실행으로 통제할 수 있다.
- 복구 가능한 백업과 롤백 담당자가 준비되어 있다.
- 점검 종료 전 검증된 복구 시간을 확보했다.

### 11.2 즉시 재개를 보류할 상황

데이터 누락, 키 충돌, 한글 손상, 날짜 이동, PDF 오연결, 업무 건수 불일치, 반복되는 SQL 오류, DB 권한 또는 TLS 연결 실패가 발생하면 서비스 재개를 보류한다. 승인 기준을 넘는 응답 지연과 잠금 문제, 중복 스케줄 실행, 복구 절차 미검증도 보류 사유다.

실패 행을 제외하고 적재를 완료한 것으로 처리하거나, 검증 차이를 설명 없이 허용하지 않는다. 예외가 업무적으로 허용되는 경우 책임자가 대상과 사유, 후속 조치 및 데이터 영향을 문서로 승인한다.

## 12 롤백과 복구 계획

### 12.1 대상 환경에서 쓰기가 발생하기 전

1. 새 애플리케이션과 스케줄러가 중지되었는지 확인한다.
2. 원본 MySQL이 T0 상태로 보존되어 있는지 확인한다.
3. 기존 WAR와 MySQL 연결 설정을 복원한다.
4. 파일 상태가 T0와 같은지 확인하고 접수 및 조회를 제한 시험한다.
5. 기존 스케줄러와 파일 소비자, 연계 요청을 순서대로 재개한다.

롤백 산출물에는 기존 WAR, 설정 참조값, 인증 정보의 복구 경로, 파일 기준선, 최종 백업, 실행 담당자와 측정 시간을 포함한다. 원본 DB에 불필요한 복원 작업을 덮어쓰는 대신 보존 상태를 먼저 확인한다.

### 12.2 대상 환경에서 쓰기가 발생한 후

연결만 MySQL로 되돌리면 MSSQL에서 생성되거나 변경된 업무가 사라질 수 있다. 신규 INSERT뿐 아니라 MASTER 상태와 건수, PDF_PATH 변경, 스케줄 삭제까지 복구 대상으로 본다.

1. 요청, 상태 수정, 모든 스케줄과 외부 파일 소비를 다시 중지한다.
2. MSSQL의 현재 DB 백업과 파일 상태를 보존하고 장애 기준 시각을 기록한다.
3. T0 원본과 동결된 MSSQL을 전체 키 기준 비교해 추가, 수정, 삭제 행을 식별한다. 대부분 테이블에는 모든 변경을 추적하는 수정 시각이 없으므로 생성 시각만으로 차분을 추출하지 않는다.
4. 검증된 역변환 및 적재 절차로 MySQL에 차이를 반영한다. 키 충돌, 자동 증가값, 시각과 문자 보존을 확인한다.
5. DB 행뿐 아니라 생성된 PDF와 JSON, 이동된 디렉터리와 외부 소비 이력을 대조한다. 발송된 작업을 자동 재처리하지 않는다.
6. MySQL과 복구 대상 업무 상태를 검증한 뒤 기존 앱을 제한 기동하고 업무 확인을 거쳐 재개한다.

생성 요청을 다시 보내는 방식은 이미 진행된 상태 변경과 삭제를 재현하지 못하므로 완전한 역이관을 대체하지 않는다. 업무 재처리를 사용할 경우 누락 없이 재현 가능한 범위와 중복 방지 방법을 별도로 승인받는다.

### 12.3 복구 목표와 전환 승인 조건

RPO는 승인된 정상 처리 요청의 유실 0을 목표로 한다. RTO와 허용 중단 시간은 리허설의 실제 복구 시간으로 확정한다. 쓰기 후 무손실 복구를 입증하지 못하면 이 목표가 달성되었다고 판단하지 않는다.

쓰기 후 역이관이 점검 시간 안에 불가능하다면 서비스 재개 전에 업무 책임자가 MSSQL에서 수정하며 운영을 복구하는 방안과 추가 중단 가능 시간을 승인해야 한다. 검증된 롤백도 없고 승인된 대체 복구 방안도 없는 상태에서는 운영 전환을 진행하지 않는다.

| 스케줄러 중복 또는 자동 시작 | 이중 파일 이동과 상태 변경 | 비활성 기동 검증, 단일 실행 책임 확정 | 운영 및 개발 |
| 부분 삭제와 부분 저장 | 고아 행 및 업무 건수 불일치 | 실패 주입 시험, 반환값과 트랜잭션 경계 점검 | 개발 |
| DB 장애로 오류 기록 실패 | 장애 원인 추적 곤란 | 앱 로그와 DB 모니터링 함께 확보 | 운영 |
| 파일과 DB 기준 시점 차이 | 출력 누락과 중복 처리 | 파일 소비자까지 통제하고 동일 기준선 기록 | 운영 및 연계 |
| 전환 후 단순 설정 롤백 | 신규 데이터와 상태 유실 | 쓰기 후 역이관 및 파일 복구 리허설 | DBA 및 개발 |
| 요청 재시도와 수동 상태 수정 누락 | 중복 접수와 업무 상태 충돌 | 요청과 운영 변경 동결, 응답 불명 목록 대조 | 연계 및 운영 |
| 테스트 환경 오접속 | 운영 데이터 변경 | 테스트 DB와 저장 경로 분리, 실행 전 접속 대상 확인 | 개발 |

## 14 역할과 책임

| 역할 | 책임 |
|---|---|
| 전환 책임자 | 일정과 범위 확정, 진행 및 중단 판단, 서비스 재개와 종료 승인 |
| 개발 담당자 | JDBC와 SQL 변경, 스케줄 제어, 기능과 장애 시험, 코드 복구 |
| DBA | 원본 조사, 대상 스키마, 이관과 정합성 검증, DB 백업과 복구 |
| 인프라 담당자 | DB 및 앱 호스트, 네트워크, TLS 인증서, 계정 연계, 파일 저장소와 모니터링 |
| 운영 담당자 | 요청과 운영 변경 동결, 앱 및 배치 통제, 실제 업무 확인과 인수 |
| 연계 담당자 | 송신 중지와 재개, 재시도 제어, 파일 소비와 발송 이력 대조 |
| 보안 담당자 | 개인정보 접근, 임시 이관 파일과 백업 보관 및 폐기 기준 검토 |

착수 시 각 역할에 실명과 대체 담당자를 배정한다. 주요 단계마다 실행자와 확인자를 기록하고, 운영 전환 중 다른 담당자가 임의로 스케줄이나 요청을 재개하지 않도록 단일 연락 체계를 사용한다.

## 15 산출물과 운영 인수

### 15.1 필수 산출물

1. 원본 DDL과 데이터 규모, DB 및 파일 의존성 조사표
2. MSSQL 대상 DDL과 자료형 매핑표, 키와 인덱스 및 권한 스크립트
3. JDBC와 SQL 변경 목록, WAR 산출물과 이전 버전 복구본
4. 이관 및 검증 실행 절차와 재실행 방법, 도구 버전 및 설정
5. 데이터 전체 비교 결과, 기능과 부하 및 장애 시험 결과서
6. 운영 전환과 쓰기 전후 롤백 리허설 결과, 단계별 소요 시간
7. 최종 전환 체크리스트와 중단 판단 시각, 연락망 및 승인 기록
8. 운영 모니터링, 백업과 복구, 스케줄러 실행 절차서
9. 원본과 신규 백업 및 임시 이관 파일의 보관과 폐기 계획

### 15.2 인수 체크리스트

- [ ] 실제 운영 배포본과 분석 대상 코드의 차이를 확인했다.
- [ ] SQL Server 버전, 스키마, 자료형, 계정과 인증서가 확정되었다.
- [ ] 원본 DDL, 기준 데이터, 키, 인덱스와 자동 증가값을 보존했다.
- [ ] 확정 SQL 7곳과 추가 호환성 수정에 대한 검증을 완료했다.
- [ ] 전체 건수, 키, 정규화된 전체 값 비교와 파일 대조를 통과했다.
- [ ] 요청 재시도와 응답 불명 요청의 처리 절차를 확정했다.
- [ ] 상태 자동 전환과 정기 삭제, 스케줄러 단일 실행을 확인했다.
- [ ] 개인정보와 오류 원문이 검증 산출물에 불필요하게 노출되지 않는다.
- [ ] 쓰기 전후 롤백의 실행 시간과 데이터 보존 방법을 검증했다.
- [ ] 운영 모니터링, 최초 업무 주기와 백업을 확인했다.
- [ ] 최종 운영 인수자와 잔여 결함 처리 담당자를 지정했다.

### 15.3 기존 환경 종료

원본 MySQL은 서비스 재개 직후 삭제하지 않고, 접근이 제한된 상태로 합의한 복구 보관 기간을 유지한다. 보관 기간은 운영과 보안 담당자가 정하며, 신규 MSSQL의 백업과 복구 검증, 운영 인수가 완료된 후 폐기 여부를 승인한다.

이관 파일, 검증 원문, 이전 설정과 백업은 개인정보 및 비밀정보 보관 정책에 따라 정리한다. 원본 환경 폐기와 데이터 보관 정책 변경은 마이그레이션 성공 여부와 별도 승인을 거친다.
